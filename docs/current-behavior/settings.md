## Current Contract

- Settings is a direct iOS primary tab on compact and regular layouts; it is not nested under More.
- User-owned preferences that should back up, restore, reset, and sync belong in SwiftData. The `UserDefaults` compatibility bridge saves and advances the synchronized preference record only when a durable value changes and applies only changed remote values back to defaults. If separate devices created duplicate logical singleton records before CloudKit imported the other device's copy, the bridge keeps the record with the newest `updatedAt`, removes the stale copies, and applies that canonical record. Device-local temporary view state never schedules the durable mirror and equivalent state is not rewritten.
- Settings -> Notifications on iOS and macOS exposes the app-wide notification toggle, the default routine reminder time, a route to system settings when authorization is disabled, and a count of the pending notification requests actually queued on that device. Pending requests are grouped by their originating task or, when the standalone Event feature is available, Event; groups are ordered by their earliest alert and expand to show that source's occurrences chronologically with the queued title, next trigger time, and explanatory text. On iOS, unavailable Event groups and Event-specific copy are omitted, and notification reconciliation does not schedule Event notifications. Each occurrence can be removed or paused for 15 minutes, one hour, until tomorrow, or a chosen later date and time. Remove skips only that occurrence; Pause replaces only that occurrence's delivery time and displays its original time. Both actions are device-local, leave source data and sibling occurrences unchanged, and use a bounded local override so notification reconciliation does not immediately recreate the skipped or original request. The list refreshes when Settings loads, when the app becomes active, after notification settings reschedule or cancel requests, and after an occurrence action; it distinguishes loading, notifications-disabled, system-authorization-disabled, and enabled-but-empty states. A one-off todo's exact reminder and, when enabled, an Event's exact notification remain inspectable on that item's detail or edit surface, while routine alerts are derived from cadence, availability, and due state. Planner and Calendar are therefore not notification ledgers, and one Advanced recurrence task can contribute several separate rolling occurrence rows under one group. Delivered alerts and future possibilities that are not currently registered with the system are not included; the pending list and its short-lived scheduling overrides are not synchronized or backed up.
- macOS development and production targets both display as `Routinam` but use different bundle identifiers (`ir.hamedgh.Routinam.mac.dev` and `ir.hamedgh.Routinam`). Notification authorization is per bundle identifier, so enabling the production app in System Settings does not authorize the development app.
- The standalone Mac Settings surface uses a launch-suppressed, single-instance standard window. It retains the system Settings command and Command-comma routing while supporting minimize, free resizing and zoom above its 640 by 560 minimum, and native full screen.
- Mac Settings -> Sections uses a segmented `Main task list` / `Backlog` picker. It shows and edits only the selected surface's custom super sections, scopes new-section creation to that surface, keeps subsections under their parent surface, and reorders top-level sections without crossing between surfaces. Existing section IDs and surface assignments are preserved.
- Top-level section names are unique within their surface, not across the whole catalog. The same name can therefore be created once in `Main task list` and once in `Backlog`; duplicate names remain rejected within the same surface, and subsection names remain unique under their parent.
- Mac Settings -> Sections expands one custom-section editor at a time. The card's height and disclosure affordance animate, while editor controls remain clipped to the rounded card and do not fade or slide independently.
- iOS and macOS Settings provide a native `Search Settings` field. It searches visible destination titles, stable aliases such as `backlog`, `sync`, `flags`, and `reminders`, and curated user-facing concepts inside each destination. Search terms and explanatory result subtitles follow the current platform: Mac can match Planner Calendar, Calendar List, keyboard shortcuts, and all four hide Flags; iOS does not advertise those Mac-only concepts and instead matches its Calendar task-review and Siri/Apple Shortcuts controls. Feature-gated destinations are excluded, and an explicit empty state appears when no destination matches.
- Task creation has no purchase entitlement or Settings override. Support & About continues to expose the general Privacy Policy and Terms of Use links. The legacy synchronized unlimited-task preference remains inert only for data-model and backup compatibility.
- Calendar task import always supports Apple Calendar. Outlook appears only when the app bundle has a nonempty Microsoft Graph client ID, so unconfigured release builds do not advertise a nonfunctional sign-in path.
- Planner Calendar configuration remains in Mac Settings -> Calendar. iOS Settings -> Calendar contains only Calendar task review/import and supplementary Persian-date display because iOS has no Planner surface that can consume the Mac preference.
- iOS Settings -> General -> `Show Home task-type control` appears only after that installation has observed its first task. When enabled, Home shows one leading task-type button that expands into All, Repeating, and One-time icon actions; choosing one immediately changes the Home list mode and its title/search scope. When disabled, Home omits that toolbar control and keeps the same task-type choice under Filters -> Task Type. Deleting every task later does not hide the setting because first-task completion is permanent for that installation. The Battery Repeating Tasks threshold likewise appears only while charge-task monitoring is enabled.
- iOS Settings -> Shortcuts always describes Quick Add, Start Focus, Today, Siri, and Apple Shortcuts. Mark Done appears only after the installation has observed a task. Shake-to-sleep, Sleep, and Wake Up appear only while both Away and the Sleep feature are enabled, matching the availability of their iOS behavior. Mac retains its keyboard-shortcut configuration and Mac-specific Settings summary.
- The iOS and macOS production bundles declare `ITSAppUsesNonExemptEncryption` as false so App Store Connect can reuse Routina's current exempt-encryption answer. The declaration must be reassessed before shipping custom cryptography, encrypted communications or VPN functionality, or a cryptography-providing dependency.
- When the matching Firebase configuration is present, iOS and macOS configure Crashlytics automatically for production crash stacks. Routina sends standard crash and device/OS diagnostics, platform and app variant, plus a throttled closed set of general interaction categories. It does not link Google Analytics, set a Crashlytics user ID, or intentionally add task content, search text, record identifiers, account details, locations, or attachments. The public Privacy Policy and the App Store Connect privacy answers must describe this collection before distribution.
- Beta Experiments are available only in development app variants. Production does not render the Beta Experiments panel after the hidden diagnostics gesture, resolves every experimental preference to disabled, and forces attempted experimental writes off, including values restored from older releases.
- The Mac production entitlement set omits location, audio input, and Apple Events automation because their Places, voice-note, and browser-automation entry points are experimental. The iOS production build likewise omits its location purpose string and compiles a no-op location client. Development builds retain those capabilities. Apple Calendar access remains a production feature and retains its calendar entitlement and purpose strings.
- Temporary, diagnostic, cache, migration, permission, and per-device handoff values can remain in `UserDefaults`.
- Hidden Support & About diagnostics show configured Data Mode and iCloud Container separately from the running executable's signed CloudKit environment. macOS reads the signed value from `com.apple.developer.icloud-container-environment`; iOS explicitly reports that this verification is unavailable rather than inferring it from configuration.
- Support & About shows the installed public Version and Build Number separately. Hidden diagnostics also shows the app's operating system and offers `Copy Diagnostics`. It copies a labelled report containing version, build number, operating-system, CloudKit, and push metadata only; it excludes user data, identifiers, credentials, and device tokens. A partial CloudKit failure includes up to three nested error codes and anonymized item fingerprints, never record names or contents.
- Debug Xcode runs maintain one bounded current performance profile and preserve one previous run before the next launch starts writing. Support & About can share either file, so reopening after a crash or force-quit leaves the most recently flushed interrupted run available until another launch rotates it. Profiles record CPU/memory symptoms, lifecycle events, and a closed interaction trail such as navigation, task-list or Timeline scrolling, filter changes, task lifecycle categories, and manual sync; each main-thread stall includes its recent interaction context. The files never include task names or identifiers, search text, tag/filter values, form content, location, account data, credentials, screenshots, or screen recording.
- iCloud sync, reset, backup import, and backup export live in one iCloud & Backup settings section. `Sync Now` verifies the manual iCloud download only; local uploads remain asynchronous and must not be reported as completed until CloudKit records a successful export. The first direct pull reads all iCloud data; after its complete response merges successfully, a per-container change token makes later pulls request only recent changes. Settings identifies that mode with a visible linear activity bar and reports the exact received-item count during a long transfer, updating after the first item and every 25 items. It does not show a percentage because CloudKit does not provide the total pending record and deletion count. Sixty seconds with no CloudKit activity is treated as a stall, while a separate three-minute hard limit bounds a continuously progressing request. A record failure, failed merge, cancellation, or timeout never advances the token; token expiry retries one full pull, and cloud reset or backup import invalidates the token. A failure states that existing local data is safe and explains whether to check the network, iCloud sign-in, or temporary service availability before using the re-enabled `Sync Now` action again. Copyable diagnostics include the actual manual-refresh mode, record counts, outcome, and sanitized error.
- Routina currently treats a configured CloudKit container as iCloud availability; it does not query `CKContainer.accountStatus`, observe `CKAccountChanged`, or retain an account-scoped identity. A person who is signed out therefore still sees `Ready to sync`, enabled `Sync Now` and cloud-reset actions, and the ordinary `Sync routines across devices` Settings summary. `Sync Now` first saves pending local SwiftData changes and then normally ends with a sign-in error from the private CloudKit database; Home pull-to-refresh and the Mac Home sync action show the same recovery message. Home, Planner, Timeline, Stats, and other product surfaces have no signed-out banner and continue presenting whatever records the local SwiftData store contains.
- Estimated iCloud Usage is an estimate of the records and media currently present in the local store, not a query of the signed-in account's CloudKit database or proof that those records uploaded. The current summary nevertheless calls locally counted rows `synced records`, including while no iCloud account is available.
- All SwiftData user models share one on-disk store configured against the build's private CloudKit container. Routina has no explicit sign-out or account-switch transition that backs up, removes, preserves, separates, or deliberately merges that local replica. Its manual direct-pull change token is scoped only by container identifier, and its legacy ubiquitous key-value preferences are likewise not account-scoped. The exact system-managed fate of the local CloudKit-backed replica after Apple Account sign-out or per-app iCloud disablement is not verified by the project; Routina therefore cannot currently promise whether every local row remains visible across that transition. The former account's server-side private-database copy is not explicitly deleted by Routina during sign-out.
- `Delete App & iCloud Data` clears the direct-pull token, deletes and saves all local SwiftData user models, clears local notifications, and only then attempts to delete the current account's private CloudKit records. If the remote step fails because the person is signed out, offline, or CloudKit is unavailable, Settings reports reset failure even though the local deletion has already completed. A successful backup from the last 24 hours is required before this sequence can begin, but the operation is not transactional across the local and remote stores.
- iOS and macOS production archives compare the current persisted SwiftData model contract with `Config/CloudKit/production-schema.manifest`. The sandboxed guard declares the manifest and every model source as exact build inputs; an unreadable input is reported as a build-configuration failure rather than a schema mismatch. A genuine mismatch blocks the archive before TestFlight upload. After deploying the Development schema in CloudKit Dashboard, the release owner explicitly acknowledges it with `script/cloudkit_schema_guard.sh --acknowledge-production-deployment --yes-i-deployed-to-production` and commits the manifest.
- Estimated iCloud Usage lists only categories whose user-facing feature is available. Tasks, logs, and images remain visible; Places, Goals, Events, Emotions, Notes, and Voice Notes follow their corresponding feature gates.
- When `Show Goals tab` is off, iOS hides Goals navigation, New Goal, Goals Stats reports, the Goals iCloud category, the Home Filters Goal option, linked Goal labels in Home task rows, and linked Goal summaries in Task Details; existing task and goal data remains stored.
- iOS Settings -> Appearance hides the Task Row `Goals` and `Places` controls, their preview content, and their shown-fields count from the respective disabled Goal and Places feature gates. Their stored row-visibility choices remain intact and return when the feature is enabled again.
- iOS Settings -> Tags does not expose saved-tag quick-filter configuration until the app provides a discoverable shortcut surface. The deferred implementation is tracked in [Product Debt 0002](../debt/0002-implement-saved-tag-quick-filters.md). On iOS and macOS, Tag Counters appears only when at least one saved Tag exists; the empty catalog shows only its Saved Tags or All Tags guidance, while the stored counter choice remains unchanged and returns with the first available Tag. iOS saved-tag counts, source summaries, empty guidance, and deletion confirmation include standalone Events only while that feature is available. Event-only tags remain stored and return when development re-enables it, and an iOS tag rename or deletion does not silently change hidden Event tags.
- The persisted built-in Flag catalog contains five behaviors for sync, backup, and Mac: Hide from Task Lists, Hide from Calendar List, Hide from Timeline, Hide from Task Ladder, and Auto Assume Done. Mac Settings and task surfaces expose all five. iOS exposes the four behaviors that have an observable iOS effect and omits Hide from Calendar List from Settings, Add/Edit Task, Task Details, and Flag filters. A Mac-originated Hide from Calendar List assignment remains stored and survives an iOS task edit; iOS simply does not present or apply it as an iOS filter choice. Settings does not describe, offer, or report migration from the discarded configurable pre-release Flag model. Launch initializes or repairs the persisted catalog to the five canonical values without scanning or rewriting task assignments.
- Default `.routinabackup` export/import and destructive reset are complete user-data operations over the SwiftData user model set. New schema-41 exports are not reported successful until an isolated restore matches the source store's canonical semantic snapshot. They contain a portable `verification.json` receipt with the manifest digest, semantic fingerprint, record counts, and every attachment's byte count and SHA-256 digest. A current package whose receipt is missing, changed, or inconsistent is rejected; older supported packages remain restorable after isolated verification and are labelled as having no source receipt.
- On a new or empty device, restore validates the selected package against that portable receipt and the real isolated restore mappings; it does not need matching data to exist on the new device. `Verify Backup` is a separate read-only action that also compares the selected package with the current local app store and reports the first semantic difference without changing data. Neither operation queries or inventories live CloudKit data, and `Sync Now` remains only a verified download operation.
- Backup import replaces the existing local user-data set rather than merging with it. It preflights the candidate, creates a verified recovery package of the destination, then stages deletion and insertion in one SwiftData transaction with one final save. A failure rolls the context back before CloudKit pull tokens or device defaults change, so it cannot commit an empty or partial replacement. Notification refresh happens afterward; its failure is a warning and does not misreport the committed data restore as failed.
- iCloud & Backup lists the ten newest verified pre-restore recovery points and can restore one through the same guarded flow. Restoring a recovery point first preserves the current state again. Recovery points live in Routina's Application Support directory: they protect a person who discovers a problem later while the app remains installed, but app deletion removes them, so moving devices or reinstalling still requires a verified export saved outside Routina.
- The project-local [`script/audit_backup.sh`](../../script/audit_backup.sh) command validates a `.routinabackup` receipt, manifest, and attachment set, restores it through the production mappings into two successive in-memory local-only stores, and compares canonical semantic exports without clearing live CloudKit tokens, applying restored preferences to device defaults, opening either app store, or contacting CloudKit. Current packages require their source receipt; older supported schemas are verified after migration for second-round-trip stability. A pass reports counts, attachment size, and a content-safe semantic fingerprint, but does not verify a later CloudKit upload, notification delivery, every screen's presentation, or available disk space during live import.
- Legacy `.json` backup remains compatibility-only for older task, place, goal, and log payloads.
- Data-wide reset actions show backup/export first when possible.
- When App Lock is enabled, opening Routina or genuinely returning to it requires one device-owner authentication attempt before tasks are shown. The temporary inactive/active scene transition created by Routina's own Face ID, Touch ID, passcode, or Mac-password prompt remains part of that same attempt and does not start another prompt. A canceled or failed attempt leaves the lock overlay visible with its manual Unlock action. Entering the background during authentication still counts as leaving Routina and requires authentication after the next return.
- Destructive data reset requires a successful local backup export from the last 24 hours and fresh App Lock authentication.
- Settings reset requires App Lock to already be enabled and a fresh successful device-owner authentication. User content remains untouched.
- Turning App Lock off requires fresh device-owner authentication.
- Production hides Devices, Places, Notes, Away, task sharing, the linked-task visualizer, Goals, Adventure, Board, advanced Query sections, Wins, Achievements, Sleep scope, and the other Beta Experiment surfaces. Previously stored experimental content remains in persistence, sync, and backups.
- Development builds expose the experiment controls in Support & About after revealing diagnostics. Their toggles continue to drive the implemented experimental surfaces for internal testing.
- iOS app and website blocking remains available in development builds, but production omits its Settings entry, Screen Time implementation, and Family Controls entitlement until Apple approves the Family Controls distribution capability. macOS blocking remains unchanged.
- While Away is unavailable, Blocking exposes only Focus mode controls and Stats hides Sleep-specific surfaces.
- Mac app widget source remains in the repository, but the Mac app targets do not build, embed, or register widget extensions, so Routina widgets are not exposed on macOS.
- macOS development runs use `script/build_and_run.sh` by default. Production launches use the explicit `--prod` path.
- The embedded macOS MCP helper inherits Routina's App Sandbox and is signed with only the App Sandbox and inheritance entitlements required for a Mac App Store helper executable.
- Mac Settings -> AI Connections explains what the local connection does, provides copyable product-help and personal-task questions, states its read-only limits and privacy boundary, and gives setup and stale-data recovery steps. The embedded helper can search and return bundled user-facing help for Task Ladder, Planner day counts, task time meanings, Assumed done, Flags and Tags, Backlog, Focus, and repeating tasks without opening the exported task snapshot; these help tools remain usable while `Allow read-only task access` is off. Enabling that device-local setting additionally exports the existing personal task snapshot for read-only task search, overdue listing, and task-detail lookup. No MCP tool creates, edits, completes, archives, or deletes Routina data.
- Both development apps honor the one-shot screenshot-data launch request and refresh Routina-owned, deterministic, date-relative fixture records without deleting unrelated development data. The fixture covers current repeating and one-time behavior, Task Ladder timing, custom Home and Backlog hierarchy, relationships, built-in Flags, links, a destination and reminder, Planner, Focus, Timeline history, and Stats-supporting activity. It creates no standalone Event or Emotion records; rerunning it removes only the two retired Event rows and ten retired Emotion rows in its reserved fixture namespace while preserving unrelated Event and Emotion history. Mac Settings -> Appearance additionally exposes `Generate Screenshot Data`; its development badge remains visible by default but can be hidden with `Show development badge`. iOS has no in-app preparation control, and production apps reject the launch trigger and hide the Mac controls.
